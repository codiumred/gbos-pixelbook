Inside the Pixelbook Port

Google built Googlebook OS for laptops from 2024 onward. Your Pixelbook is from 2017. Getting one onto the other meant working at every level of the machine: the CPU, the kernel, the drivers, Android's own startup scripts and security rules. This page walks through each level, what Google ships, what we changed, and why.

Chapter 2

The CPU problem, and the trap lab

A program is a list of instructions the CPU knows. Every few years Intel adds new ones. Google compiled Googlebook OS for newer chips, so its programs contain instructions your Kaby Lake CPU has never heard of: GFNI, AVX-VNNI, SHA-NI and wide VAES. When the CPU meets one, it stops and raises an "invalid opcode" fault, and normally the program dies. The very first program Android starts, init, contains them. Without help, the system dies within two seconds of starting. verified in QEMU

Our fix lives in the kernel. When the fault happens, the kernel decodes the unknown instruction, computes what it would have done using instructions the CPU does have, writes the result back and lets the program continue. The program never notices. This is called trap and emulate. It works, but each trap costs thousands of times more than a normal instruction, so hot loops full of them are slow. That's where the shortcuts come in.

How we know the emulator is correct

An emulator that is subtly wrong corrupts data silently. So every emulated instruction was compared against a real CPU that has it: 225 million random test cases on the development PC (an i7-13700). Then the whole thing ran inside a virtual Kaby Lake-class CPU, booting Google's unmodified system with zero crashes from missing instructions. verified

Still open: wide AES (VAES) and carry-less multiply traps from HTTPS and the Tethering module, and GFNI, which now dominates the remaining count. These cost speed, not correctness.

Chapter 4

Case file: the audio freeze

Starting with v10, the laptop froze solid the moment Android opened the speaker. No error ever reached the log, because the log is written to the slow USB stick and the machine died first. Two tricks cracked it. First, Google's own chromeos_pstore driver keeps a copy of the kernel's messages in a reserved piece of RAM that survives a warm reboot. Second, a special boot entry made every freeze detector crash and reboot the machine instead of hanging. The next boot found the crash report waiting in RAM. verified

The report pointed at one function in Google's audio-chip driver, avs_path_set_constraint. Step through it below to see the bug.

Speaker path template (example shape) inferred

Why a small bug froze everything

Google compiled this driver with automatic bounds checks: writing past the end of an array triggers a deliberate crash instead of silent memory corruption. That crash happened inside the audio service's thread while it held the sound system's locks. Everything that wanted sound then waited forever, and the whole machine stopped responding.

How we replaced it safely

Google ships this driver as a separate module, so we couldn't just edit the kernel. We rebuilt the module from the same source with a one-line-idea fix: size the arrays by modules, not by paths. Three checks prove it matches Google's: 268 identical symbol versions, the same options and the same function list. A startup rule swaps it in about 20 milliseconds before Android's driver loader starts.

Chapter 5

Why Continue On is blocked

Continue On streams your phone's apps to the laptop over your local network. Before the phone agrees, it wants proof that the laptop is a genuine, untampered device. That proof is a chain of trust that starts in the factory. Switch between a real Googlebook and this Pixelbook to see where the chain breaks.

Patching the laptop to believe it passed wouldn't help. The verdict is signed by Google's servers, and the phone checks it. GMS on the laptop has validate_remote_device_integrity = true, which means each side checks the other. Faking the signed verdict means faking factory keys, which is the route we decided not to take.

Reference

Glossary

Kernel

The core program that owns the hardware: memory, CPU time, devices. Everything else asks it for things. Android's kernel is Linux. Google publishes the source, which is why we could rebuild it.

Driver / kernel module

Code that teaches the kernel one piece of hardware. A module is a driver kept in a separate file and loaded on demand. Google ships hundreds; ours must match their "symbol versions" exactly, or the kernel refuses to load them.

Symbol versions (CRCs)

Fingerprints of every function and data shape the kernel offers modules. If one changes, a module built for the old shape could corrupt memory, so the kernel refuses it. Our rebuilt kernel had 0 mismatches against Google's 643 modules.

Trap / #UD / invalid opcode

The CPU's reaction to an instruction it doesn't know: it stops the program and hands control to the kernel. Normally the kernel kills the program (SIGILL). Ours emulates the instruction instead.

Fast path

Instead of trapping on every SHA instruction inside a hash function, the kernel recognises the whole function by a fingerprint of its bytes on the first trap, runs an equivalent C version and jumps to the function's end.

init, ueventd, HAL

init is Android's first program; it reads .rc scripts and starts everything else. ueventd watches for hardware and loads matching modules. A HAL (hardware abstraction layer) is a service that turns hardware into an Android API, like the audio HAL "dras" or the camera HAL.

SELinux policy

Android's rulebook of which program may touch which file or device. Anything not explicitly allowed is denied. Several of our fixes were one-line additions to it.

GBRUNCH, GBVENDOR, GBLOG

Partitions added by gbrunch, the project we build on. GBRUNCH (/oem) holds our startup scripts and overlay files; GBVENDOR is a copy of Google's vendor partition with policy changes; GBLOG stores logs you can copy off the stick. Google's own partitions stay byte-for-byte unchanged.

Bind mount

Making one file appear in place of another without changing either. We use it to put our zlib, audio config and fixed audio driver over Google's read-only files.

Attestation / Play Integrity

Cryptographic proof, rooted in keys burned in at the factory and registered with Google, that a device runs untampered software. Google's server refuses this device's keys ("Device not registered"), so features that require proof are unavailable.

ramoops / pstore

A reserved area of RAM where the kernel keeps its recent messages. It survives a warm reboot, so after a crash the next boot can read what happened. It is how we caught the audio bug.
